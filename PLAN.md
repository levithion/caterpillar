# PLAN.md

## Project idea

**Smart Operator Assistant** is an end-to-end intelligent companion for CAT machine
operators (excavators, loaders, etc.). Instead of a single-purpose tool, it wraps a
day's work in one interface: what to do, whether it's being done safely, how to get
better at doing it, and how long it should take.

The brief (see `CLAUDE.md`) calls for five outcomes:

1. **Daily task dashboard** — the day's scheduled tasks at a glance.
2. **Safety features** — seatbelt compliance, proximity hazards, incident logging.
3. **Operator training hub** — e-learning content, instructor booking, or simulation.
4. **Anomaly detection** — flag unusual usage (excessive idling, unsafe patterns).
5. **Task time estimation** — predict completion time from history + conditions.

The dataset (`data/*.csv`, generated by `scripts/generate_data.py`) is synthetic but
shaped like real fleet telemetry: machines, operators, tasks, a telemetry time series,
incidents derived from flagged telemetry, and a training catalog + per-operator
progress. Everything joins on `Machine ID`, `Operator ID`, and `Module ID`.

## Architecture

- **Backend** — FastAPI (`backend/app`), reading the CSVs directly with pandas
  (no database yet). Exposes REST endpoints per domain object plus two derived
  endpoints: `/api/anomalies` (z-score outlier detection over telemetry) and
  `/api/predict/task-time` (a scikit-learn `RandomForestRegressor` trained on
  historical completed tasks).
- **Frontend** — Vite + React + TypeScript (`frontend/src`), a tabbed single-page
  app (`Dashboard`, `Safety`, `Training`, `Anomalies`, `Predictor` components)
  calling the backend over `fetch` (`frontend/src/api.ts`).
- **Data** — flat CSVs as the system of record for this prototype; swapped for a
  real telemetry feed / database later without changing the API surface.

## Execution steps (remaining)

### 1. Backend hardening
- [ ] Cache `load_all()` (currently re-reads every CSV on every request) — load once
      at startup, or memoize with a `functools.lru_cache` / file-mtime check.
- [ ] Persist the trained task-time model instead of retraining lazily on first
      request (train at startup, or cache to disk with `joblib`).
- [ ] Add `/api/dashboard/{operator_id}` or `?date=` filtering so the frontend
      doesn't need to fetch and filter all tasks client-side.
- [ ] Basic input validation / error responses for unknown machine/operator IDs.
- [ ] Tests: at least smoke tests for each endpoint and the anomaly/prediction logic
      (`pytest` — not yet in `requirements.txt`).

### 2. Safety features (currently data-only)
- [ ] Seatbelt compliance: surface live/most-recent `Seatbelt Status` per
      machine-operator pair, not just raw telemetry rows.
- [ ] Proximity hazards: turn `Proximity Distance` / `Proximity Alert` into a
      ranked "active hazards" view instead of a flat table.
- [ ] Incident logging: add a way to *create* an incident from the UI (currently
      read-only), wired to `POST /api/incidents`.

### 3. Training hub
- [ ] Decide the "creative learning format" for this prototype (recommend:
      e-learning video catalog + a lightweight quiz/simulation stub — an
      instructor-booking calendar is higher effort for similar demo value).
- [ ] Show certification-expiry warnings (`Certification Expiry` in
      `training_records.csv`) prominently, since that's a real operational risk.

### 4. Anomaly detection
- [ ] Expand beyond idling/fuel z-scores to pattern-based flags (e.g. repeated
      `Safety Alert Triggered` events, RPM/load-cycle combinations).
- [ ] Surface anomalies in the Dashboard tab (currently its own separate tab),
      since operators shouldn't have to go looking for them.

### 5. Task time estimation
- [ ] Show a confidence range, not just a point estimate (e.g. quantile regression
      or the RandomForest's per-tree spread).
- [ ] Feed the predicted time back into the Dashboard task list ("est. vs predicted").

### 6. Frontend polish
- [ ] Loading/error states for all `fetch` calls in `api.ts`.
- [ ] Replace tab-only navigation with a real dashboard landing view once safety +
      anomalies are cross-linked (see 2 and 4 above).
- [ ] Basic responsive layout check (this is meant to run in-cab, likely on a
      tablet-sized screen).

### 7. Ops / deployment
- [ ] `docker-compose` (or similar) to run backend + frontend together for demo.
- [ ] CI: lint (`oxlint`, backend `ruff`/`black` if added) + test on push.
- [ ] Replace synthetic CSVs with a real ingestion path before any production use
      (explicitly called out in `CLAUDE.md`).

## Suggested next milestone

Ship a coherent demo: cached data loading + trained-at-startup model (1), incident
creation (2), certification-expiry banner (3), anomalies surfaced on the dashboard
(4), and predicted time shown per task (5). That turns the five outcome areas from
independent tabs into one connected assistant, which is the actual ask in the brief.
